# PROTOCOL_SPEC.md — TAKD-PQE Implementation Specification

Derived from: "QYMail-TEF: A Post-Quantum, Hardware-Attested, Dual-Entropy-Anchored Key Agreement
Protocol for Secure Electronic Mail" (Sections V, VI-A, Table II). This document is implementation-level —
it does not re-derive security proofs; see the paper for those. Where the paper is precise at the research-
paper level of abstraction but not fully explicit at wire-format precision, the gap is marked
**[IMPLEMENTATION DECISION]** and must be logged verbatim into `DECISIONS.md` the first time it's
implemented, per Global Rule R7.

---

## 1. Notation (from paper Table II — do not rename these in code without updating this doc)

| Symbol | Meaning | Size |
|---|---|---|
| session_id | 16-byte unique session identifier, generated by server | 16 B |
| TS | Timestamp | — |
| pkS / skS | Ephemeral ML-KEM-1024 key pair | pk: 1568 B |
| pksig,P / sksig,P | Long-term ML-DSA-87 identity key pair per party P | — |
| ct / ss | KEM ciphertext / shared secret | ct: 1568 B, ss: 32 B |
| TEFC / TEFS | 32-byte physical (emulated) noise samples, client/server | 32 B each |
| rC / rS | 16-byte commitment blinding nonces, client/server | 16 B each |
| CommitC / CommitS | SHA3-256 commitments to TEF values | 32 B each |
| THi | Running transcript hash after message Mi | 32 B |
| Kwrap,C / Kwrap,S | HKDF-derived AEAD keys for TEF reveal (M4/M5) | 32 B each |
| Fusion | SHA3-256(TEFC ∥ TEFS ∥ session_id) | 32 B |
| SessionKey | Master symmetric key for body AEAD | 32 B |
| MAC1 | Server's key-possession proof in M3 | — |
| MACS / MACC | Key-confirmation tags in M5 / M6 | — |
| quote | SHM attestation quote (device_id, firmware_hash, ephemeral pubkey, session_id, timestamp) | — |
| SigS | ML-DSA-87 signature over `quote` under the server's long-term signing key | 4627 B |

## 2. Message Wire Formats

All fields are canonically serialized per `crypto/serialization.py` (Global Rule R2: two different
serializations of the same logical message must be structurally impossible — use a fixed field order and
a fixed encoding, e.g. length-prefixed CBOR or a fixed JSON key order with no whitespace variance).

### M1 (Server → Client)
```
{
  session_id: bytes(16),
  TS: uint64,                       // server-generated timestamp
  pkS: bytes(1568),                 // ephemeral ML-KEM-1024 public key
  quote: {
    device_id: string,
    firmware_hash: bytes(32),
    ephemeral_kem_public_key: bytes(1568),   // == pkS, bound explicitly
    session_id: bytes(16),
    timestamp: uint64
  },
  SigS: bytes(4627)                 // ML-DSA-87 sig over SHA3-256(canonical(quote)), server's long-term key
}
```
Server-side actions: generate ephemeral ML-KEM-1024 keypair (pkS, skS) via SoftwareSHM; build `quote`
binding pkS to device identity; sign SHA3-256(canonical(quote)) with long-term ML-DSA-87 key; set
`TH0 = SHA3-256("QYMail-init" || session_id)`; set `TH1 = SHA3-256(TH0 || canonical(M1))`.

Client-side verification on receipt: recompute TH1 the same way; verify SigS against the server's known
long-term public key (out of scope: PKI/trust-establishment for that public key itself — assume it is
already known/pinned for the prototype, and say so explicitly in DECISIONS.md); verify
`quote.ephemeral_kem_public_key == pkS` (attestation-to-key binding check); verify `quote.session_id ==
session_id`. Any failure → abort, do not proceed to M2.

### M2 (Client → Server)
```
{
  session_id: bytes(16),
  ct: bytes(1568),                  // KEM.Encaps(pkS) ciphertext
  CommitC: bytes(32)                // SHA3-256(TEFC || rC || session_id)
}
```
Client-side actions: `(ct, ss) = KEM.Encaps(pkS)`; SoftwareSHM generates `TEFC` (health-tested) and
random `rC`; `CommitC = SHA3-256(TEFC || rC || session_id)`; `TH2 = SHA3-256(TH1 || canonical(M2))`.

**Ordering guarantee (structural, not just conventional):** the client MUST compute and send CommitC
before receiving CommitS in M3 — enforce this by making CommitC construction have no dependency on
any server-supplied value received after M1. This is what the paper's bias-resistance argument (Theorem 4)
relies on; verify it structurally in Stage 4's code review, not just by testing behavior.

### M3 (Server → Client)
```
{
  CommitS: bytes(32),               // SHA3-256(TEFS || rS || session_id)
  MAC1: bytes                       // HMAC(TK, "commit" || TH2)
}
```
**[IMPLEMENTATION DECISION]** `TK` ("transport key," per the paper's MAC1 formula) is not explicitly
derived elsewhere in the paper text. Implementation choice: derive `TK = HKDF-Expand(HKDF-Extract(salt=
b"", ikm=ss), info=b"QYMail-TK-v1", length=32)` — i.e., an early, ss-only-keyed HKDF output, computed
before Fusion is available (Fusion requires both TEFs, which haven't been revealed yet at M3). This lets the
server "prove possession of ss without revealing key material," per the paper's own description of MAC1's
purpose, using only material both sides already have after M2 (ss, from KEM.Decaps on server side once
it processes M2's ct). Log this in DECISIONS.md on first implementation.

Server-side actions: SoftwareSHM generates `TEFS` (health-tested) and random `rS`; `CommitS = SHA3-
256(TEFS || rS || session_id)`; decapsulate `ss = KEM.Decaps(skS, ct)` from M2; derive `TK` per the
decision above; `MAC1 = HMAC(TK, "commit" || TH2)`; `TH3 = SHA3-256(TH2 || canonical(M3))`.

Client-side verification: recompute TH3; independently derive `TK` (client already has `ss` from its own
`KEM.Encaps` call) and verify MAC1. Failure → abort.

### M4 (Client → Server)
```
{
  wrappedC: bytes                   // AEAD.Encrypt(Kwrap,C, TEFC || rC, AD = TH3)
}
```
Client-side actions: derive `Kwrap,C = HKDF-Expand(HKDF-Extract(salt=b"", ikm=ss), info=b"QYMail-
KwrapC-v1", length=32)`; encrypt `TEFC || rC` under ChaCha20-Poly1305 with `Kwrap,C`, associated data =
`TH3` (per paper: "with TH3 as associated data" — this one is explicit in the paper, no decision needed);
`TH4 = SHA3-256(TH3 || canonical(M4))`.

Server-side verification: recompute TH4; decrypt `wrappedC` with `Kwrap,C` (server derives the same key
from its own `ss`) and AD = TH3, reject on AEAD auth failure; recover `TEFC, rC`; verify
`SHA3-256(TEFC || rC || session_id) == CommitC` (from M2) — this is the binding check. Failure at either
step → abort.

### M5 (Server → Client)
```
{
  wrappedS: bytes,                  // AEAD.Encrypt(Kwrap,S, TEFS || rS, AD = TH4)
  MACS: bytes                       // key confirmation tag
}
```
**[IMPLEMENTATION DECISION]** The paper states M4's AD is explicitly TH3, but does not restate the AD
for M5 with the same explicitness. Implementation choice, for consistency with the transcript-binding
design rationale stated in paper Section V ("Transcript binding renders reordering, truncation, or field
injection immediately detectable"): use `AD = TH4` for `wrappedS`, i.e., the same "AD = transcript hash at
time of previous message" pattern as M4. Log this in DECISIONS.md.

**[IMPLEMENTATION DECISION]** `MACS` construction: the paper states MACS is a "key confirmation" tag
sent after `Fusion` and `SessionKey` are derived, following the same pattern as `MAC1`/`MACC`.
Implementation choice: `MACS = HMAC(SessionKey, "confirm-S" || TH5)`, computed after TH5 is set.

Server-side actions: derive `Kwrap,S` analogously to `Kwrap,C` but with a distinct label (`b"QYMail-
KwrapS-v1"`); encrypt `TEFS || rS` under `Kwrap,S` with AD = TH4; compute `TH5 = SHA3-256(TH4 ||
canonical(M5-minus-MACS))` — **note:** TH5 must be computed over the message content that MACS itself
authenticates, so MACS cannot be part of the input to its own transcript hash; compute this as
`TH5 = SHA3-256(TH4 || canonical({wrappedS}))`, then `MACS = HMAC(SessionKey, "confirm-S" || TH5)`,
and the actual M5 sent on the wire includes both `wrappedS` and `MACS`; compute `Fusion = SHA3-
256(TEFC || TEFS || session_id)` (server now has both TEFs); derive `SessionKey` via HKDF-Extract-Expand:
`PRK = HKDF-Extract(salt = Fusion, ikm = ss)`, `SessionKey = HKDF-Expand(PRK, info = b"QYMail-
SessionKey-v1", length = 32)` (per paper: "HKDF extract-then-expand... keyed by ss and salted with
Fusion").

Client-side verification: decrypt `wrappedS` with `Kwrap,S` and AD = TH4, reject on AEAD failure; recover
`TEFS, rS`; verify `SHA3-256(TEFS || rS || session_id) == CommitS` (from M3); compute `Fusion` and
`SessionKey` identically to the server; recompute `TH5` the same way the server did; verify `MACS` using
its own derived `SessionKey`. Failure at any step → abort.

### M6 (Client → Server)
```
{
  MACC: bytes                       // key confirmation tag
}
```
**[IMPLEMENTATION DECISION]** By symmetry with MACS: `TH6 = SHA3-256(TH5 || canonical(M5))`,
`MACC = HMAC(SessionKey, "confirm-C" || TH6)`.

Client-side actions: compute TH6, MACC, send M6.
Server-side verification: recompute TH6 and expected MACC; verify. On success → session state =
`ESTABLISHED` on both sides, both parties hold identical `SessionKey`. On failure → abort.

## 3. HKDF Label Registry (Global Rule R2 — every derived key needs a distinct label)

| Label | Purpose | Derived from |
|---|---|---|
| `QYMail-TK-v1` | MAC1 transport key (M3) | ss only |
| `QYMail-KwrapC-v1` | Client TEF-reveal AEAD key (M4) | ss only |
| `QYMail-KwrapS-v1` | Server TEF-reveal AEAD key (M5) | ss only |
| `QYMail-SessionKey-v1` | Final body-encryption key | ss, salted by Fusion |

All four MUST produce distinguishable outputs even though three of them share `ikm = ss` — this is exactly
what Invariant #5 in Stage 5 (`HKDF label separation`) tests.

## 4. Transcript Construction (paper Section V, explicit — no decisions needed)

```
TH0 = SHA3-256("QYMail-init" || session_id)
THi = SHA3-256(TH(i-1) || canonical(Mi))   for i = 1..6
```
`canonical(Mi)` must use the exact same serialization function for both hashing and for constructing AEAD
associated data, so a party that authenticates against THi is authenticating the literal bytes that were
transcript-hashed.

---

## 5. Commitment Construction (paper Section V, explicit)

```
CommitC = SHA3-256(TEFC || rC || session_id)
CommitS = SHA3-256(TEFS || rS || session_id)
```
Hiding property: without knowing `TEFX`, `Commit` reveals nothing (informally, since SHA3-256 is modeled
as a random oracle for this purpose per paper Section VI-B assumption A2).
Binding property: a party cannot later reveal a different `(TEFX, rX)` pair that also hashes to the same
commitment (collision resistance of SHA3-256).

---

## 6. Fusion Construction (paper Section V + Table II, explicit)

```
Fusion = SHA3-256(TEFC || TEFS || session_id)
```
Computed by the server first in M5 (has both TEFs by then), and independently recomputed by the client
after decrypting `wrappedS` in M5. Never transmitted on the wire — both sides derive it locally.

## 8. State Machine

```
INIT
  → M1_CREATED (server) / M1_VERIFIED (client, on valid M1)
  → M2_CREATED (client) / M2_VERIFIED (server, on valid M2 + matching session_id)
  → M3_CREATED (server) / M3_VERIFIED (client, on valid MAC1)
  → M4_CREATED (client) / M4_VERIFIED (server, on valid AEAD + commitment match)
  → M5_CREATED (server) / M5_VERIFIED (client, on valid AEAD + commitment match + valid MACS)
  → M6_CREATED (client) / M6_VERIFIED (server, on valid MACC)
  → ESTABLISHED (both sides)
  → EMAIL_SECURE (in use for message send/receive)
  → TEARDOWN (on session expiry/close)
  → ZEROIZED (terminal)
```
Any transition attempted out of this exact sequence (e.g. M4 arriving before M3_VERIFIED) MUST raise
`InvalidStateTransition` and abort the session — this is Stage 4's core deliverable and Stage 5's Invariant #10.

## 9. Explicit Non-Goals for This Spec (deferred to later stages / out of scope)

- Server long-term ML-DSA-87 public key distribution/pinning mechanism (assume pre-shared/pinned for the
  prototype; a full PKI is out of scope, consistent with the paper's own scope).
- Session resumption / key caching (Stage 8 may add this; if not, every send re-runs M1-M6 and that must
  be stated plainly, not left ambiguous).
- Multi-recipient fan-out (single sender/recipient pair only for the hackathon prototype).
